# 04 · 电梯调度

> 本作区别于 Mini Metro 的"招牌机制"。MVP 只做自动扫楼，策略层后置。
> 关联：[03 · 寻路](03-pathfinding.md)（等车估算依赖轿厢当前状态）。

---

## 1. 调度 vs 寻路的边界

| 层 | 负责 | 不负责 |
|---|---|---|
| **寻路（route.ts）** | 乘客"该乘哪部梯、在哪换乘" | 电梯该不该停 |
| **调度（dispatch.ts）** | 电梯"沿停靠表运行、停不停、接不接客、是否空驶" | 乘客个人计划 |

两者通过"轿厢状态（位置/方向/载客）"耦合：寻路用它估算等车，调度按策略决定停靠。

## 2. 轿厢状态机

```
        ┌────────┐  有请求   ┌────────┐  到达目标层  ┌────────┐
        │ IDLE   │ ───────▶ │ MOVING │ ──────────▶ │ DWELL  │
        │ (待命) │          │ (运行) │             │ (停靠) │
        └────────┘ ◀─────── └────────┘ ◀────────── └────────┘
             ▲                    │                     │ 装载/卸载
             │  无请求            │ 到端点反向           │
             └────────────────────┴─────────────────────┘
```

- `MOVING`：向 `targetFloor` 移动，逐帧更新 `pos`（浮点楼层）。
- `DWELL`：开门，先卸后装（受容量与策略约束），持续 `DWELL_TIME`。
- `IDLE`：无目标，等待新请求（按策略可能回到大堂/待命层）。

## 3. MVP 调度：SCAN / LOOK（扫楼）

最简单且稳定的自动调度：

```
轿厢维护一个方向 dir（上/下）与停靠表 stops。
循环：
  若 dir 方向上还有"需要服务的站"（有需在此上下客的请求）：
      前往下一个这样的站，停靠处理
  否则：
      dir 取反；若反向也没有请求，则 IDLE
```

- "需要服务的站" = 该层有乘客计划乘坐本梯（上/下），或本梯有乘客要在此下。
- 顺向接客，到端点反向。这就是经典 **LOOK 算法**（电梯领域最常用）。

## 4. 调度策略（每梯一个枚举，后置到 M2）

| 策略 | 行为 | 适用 |
|---|---|---|
| `SCAN`（默认） | 上下往复扫楼，顺向接客 | 通用 |
| `ZONE` | 只服务自身停靠表内的请求，不回大堂外 | 分区楼 |
| `UP_PEAK` | 大堂满载 → 直达最高需求层 → 本地下行卸客 → 空驶快返大堂 | 早高峰 |
| `DOWN_PEAK` | 高层满载下行 → 逐层卸 → 空驶返高层 | 晚高峰 |
| `ALL_CALL` | 不区分方向，来者就停（低效但公平） | 教学/公平场景 |

实现建议：策略只是"停靠判定函数"的枚举，不建策略框架/类继承。

```ts
function shouldStop(elev, floor, pending, phase): boolean {
  switch (elev.policy) {
    case 'SCAN':     return pending.hasCall(elev, floor, elev.dir);
    case 'ZONE':     return elev.stops.includes(floor) && pending.hasCall(elev, floor, elev.dir);
    case 'UP_PEAK':  return phase === 'morning'
                       ? (floor === LOBBY && elev.load > 0 || pending.down(elev, floor))
                       : shouldStopScan(elev, floor, pending);
    case 'ALL_CALL': return pending.anyCall(elev, floor);
  }
}
```

## 5. 接客判定规则

乘客登梯需同时满足：
1. 有该梯的计划（`passenger.plan` 下一段 = 本梯且 `boardFloor` = 当前层）；
2. 轿厢未满载（`load < capacity`）；
3. 策略允许（如 `SCAN` 要求方向一致；`ALL_CALL` 不要求）。

若满载，乘客留在原地（`WAIT`/`TRANSFER` 继续计耐心）。可选：记录"跳过次数"用于诊断。

## 6. 空驶返程（deadhead）优化

早高峰的最优不是"跟着乘客慢慢下去"，而是：
**满载上行 → 顶层卸空 → 空车快速回落大堂 → 再接一批。**

- 由 `UP_PEAK` / `空驶优化` 策略实现：无下行请求时，直接设 `targetFloor = LOBBY` 且沿途不停。
- 这是本作相对 Mini Metro 的策略增量，也是"调度魂"的体现。

## 7. 扩展方向（后置，不在 MVP）

- **线路分组**：同路线多轿厢共享节点，等车估算取"下一班"，实现"频率"概念（类比 Mini Metro 多列车）。
- **预测调度**：依据历史/当前需求预测下一分钟客流，提前把空梯调往高需求层。
- **优先级**：VIP/担架/无障碍乘客的优先接载与专梯。
- **故障与冗余**：轿厢下线后其余车辆的自动再平衡。

## 8. 参数

| 参数 | 含义 | 建议初值 |
|---|---|---|
| `CAPACITY` | 单轿厢载客数 | 8–16 |
| `SPEED` | 层/秒 | 1–2 |
| `DWELL_TIME` | 每站停靠秒数 | 2–4 |
| `IDLE_FLOOR` | 待命/返程目标层 | 大堂(1F) |
| `SKIP_COOLDOWN` | 满载跳过后冷却 | 0 |

## 9. 不做清单

- ❌ 策略类继承体系 / 插件框架
- ❌ 群体智能 / 强化学习调度（个人实验不需要）
- ❌ 每帧重排全部请求
