# 06 · 路线图与 MVP

> 目标：**每一步都能看到能跑的东西**，绝不一次性搭大架子。
> 关联：[02 · 架构](02-architecture.md)、[03 · 寻路](03-pathfinding.md)。

---

## MVP 定义（"最小可玩"）

一栋楼、少量电梯、乘客上下行、可编辑停靠表、能换乘、能因拥挤而输、能在早中晚潮汐下存活若干天。

**MVP 验收**：能连续玩 3 天不崩；输掉时能指出是哪层成为瓶颈；改一条线路能明显改变结果。

---

## M0 · 骨架（半天）

**目标**：主循环与可视化跑起来，能编辑停靠表。

- [ ] `index.html` + 单文件（或拆 `main.ts/render.ts`）
- [ ] 固定步长主循环（见 02 §4）
- [ ] 画大楼剖面：楼层横线 + 编号
- [ ] 一部电梯沿停靠表上下往复（无乘客）
- [ ] 拖拽编辑该电梯的停靠表，实时生效
- [ ] 空格暂停

**验收**：改停靠表，电梯路径立即变化；60fps。

## M1 · 核心（1–2 天）

**目标**：出现乘客与胜负。

- [ ] 楼层生成乘客（`from → destZone`，上下行，耐心的计时）
- [ ] 登梯/下梯/满载判定
- [ ] 寻路：先 **BFS（换乘数→站数）** 通链路（见 03 §8）
- [ ] 楼层压力条 + 拥挤失败
- [ ] 简单 HUD（时间、送达数、当前时段）

**验收**：乘客能完成一趟直达；某层挤爆会结束游戏。

## M2 · 灵魂（2–3 天）

**目标**：换乘 + 调度策略 + 时段，出现"设计感"。

- [ ] 升级为带权 **A\***（含等车估算、换乘/回头惩罚，见 03）
- [ ] 换乘：多梯共停层的上下梯衔接
- [ ] `SCAN` 自动调度（见 04）
- [ ] 早/午/晚/夜四时段需求曲线
- [ ] 一到两种调度策略（`UP_PEAK` 早高峰）
- [ ] 换乘可视化（颜色连线/高亮）

**验收**：设计一条"低区+高区+空中大堂"的换乘网络，早高峰吞吐明显优于单梯直达。

## M3 · 元循环（按需）

**目标**：每日升级、楼长高。

- [ ] 每天结束的升级二选一（新梯/容量/速度…）
- [ ] 楼层加建 + 租户入驻
- [ ] 评分与星级
- [ ] （可选）seed + 命令流存档/回放

**验收**：连续生存递增天数；升级选择影响后续策略。

## M4 · 打磨（按需）

- [ ] 突发事件系统（停电/检修/演练/VIP）
- [ ] 音效（WebAudio 振荡器"叮"）与时段光照
- [ ] 多建筑地图（办公楼/医院/商场/酒店/超高层）
- [ ] 跨楼连廊、双层轿厢等进阶升级
- [ ] 移动端触控

---

## 平衡与测试策略

1. `sim.ts` 纯逻辑 ⇒ `node` 无头跑 1000 局。
2. 输出 KPI：平均等待 / 最大等待 / 送达 / 换乘 / 能耗 / 失败楼层。
3. 只改 `config.ts` 系数，观察 KPI 变化，逼近目标曲线。
4. 确定性 seed ⇒ 同一局可反复对比不同参数。

## 风险与缓解

| 风险 | 缓解 |
|---|---|
| 换乘网络设计不出来（玩法不成立） | M2 验收即验证；不成立则退化为"纯电梯调度优化" |
| 寻路抖动（乘客来回换乘） | 先不做 2017 阈值；出现时再加 `BACKTRACK_PENALTY` / 紧凑换乘阈值 |
| 数值难调 | 无头跑分 + 数据驱动 |
| 越做越大 | 见下方"不做清单"，每阶段自检 |

## 不做清单（每阶段自检）

- ❌ PixiJS / Phaser / Godot（MVP 阶段）
- ❌ ECS 框架、事件总线框架、状态库
- ❌ JSON 配置系统
- ❌ RAPTOR / 时间依赖图 / 容量预测
- ❌ 后端 / 网络 / 多人
- ❌ 3D / 剧情 / 开放世界
- ❌ 存档回放（M3 之前）
